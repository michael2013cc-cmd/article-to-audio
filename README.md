# article-to-audio

把一篇**给人看**的文章，变成一个**能听**的单档 mp3。

> Turn a long text article into one listenable mp3: rewrite the prose for speech,
> synthesize in batches, merge into a single file, and verify by transcribing it back.

不是「调一下 TTS 接口」。是把散文改写成口语稿、分段合成、合并、**再转写回来验证**。

```
文章（表格 / 百分比 / 中英夹杂 / 满屏引用链接）
  ↓  ① 改写为口语稿     ← 真正的活在这里
分段 JSON
  ↓  ② 批量合成 + 排序 + 下载 + 合并 + 回听校验
narration.mp3 + narration_script.md
```

---

## 为什么值得单独做一个 skill

因为「念出来」这件事的失败点，**不在合成环节**。

| 给眼睛看 | 给耳朵听 | 由此产生的失败 |
|---|---|---|
| 可以回头查 | 听过去就没了 | —— |
| `+1.79%` | 念成「加一点七九趴」 | 符号没转口语 |
| markdown 表格 | 一行一格地念，像念经 | 表格没线性化 |
| `alt／label` | 念成两个英文词，听者一脸茫然 | 缩写没处理 |
| 引用链接 | 15 个字符的 URL 一个个读出来 | 链接没剥 |
| 第 3 段 | 跑到第 7 段去了 | 接口返回顺序 ≠ 请求顺序 |

**最后一条是工程坑，前面几条是内容判断 —— 没有任何 TTS 引擎会替你做。**

---

## 架构：判断层与确定性层是分开的

这是这个项目最核心的设计。

```
┌──────────────────────────────────────────────┐
│  LLM 判断层（SKILL.md · procedure）            │  ← 换一篇文章就要重新判断
│  · 表格 → 叙述句                              │     规则有例外，不该脚本化
│  · 符号 → 口语                                │
│  · 术语三分法（展开 / 保留+注解 / 替换语义）     │
│  · 剔除元内容，并明确告知用户                   │
└──────────────────────────────────────────────┘
                 ↓ segments.json
┌──────────────────────────────────────────────┐
│  确定性层（narrate.mjs · 213 行 · 零依赖）     │  ← 同样输入永远同样输出
│  · 分批调用（>10 段自动拆批）                   │
│  · 响应重排 + 文件名全量断言                    │
│  · 下载 / 合并 / 段间 0.5s 停顿                 │
│  · 字秒比交叉验证 + 转写回听                     │
└──────────────────────────────────────────────┘
```

把判断塞进脚本 → 得到一张又长又脆的正则表。
把确定性留给 LLM → 每次重新踩同一个坑（顺序错乱这个坑，**连踩三次**）。

## 特色

### 1. 校验链：合成完不算完成

生成之后，**把音档丢回 STT 转写回来，比对文章的关键数字**。

不是听起来像，是逐项验：

```
STT 10720 chars; 21/21 keys matched
```

`--verify` 传的是「这篇的承重数字」——营收、市占率、判决金额。数字对了，音轨才可信。

顺带查出一个真 bug：`94%` 第一轮没命中，复跑中了。**是切片边界的识别波动，不是内容错误。** 没有这套链，这种情况会被当成「生成失败」而重做。

### 2. 长音频切片转写

STT 服务对 **33MB / 35 分钟的整档会静默返回 0 字** —— 不报错，就是空的。

脚本自动按 5 分钟切片、转写、合并。7 片全过。

### 3. 字秒比交叉验证

每段音频时长 ÷ 文本字数，落在 4.7–5.9 字/秒区间。**某段比值突然离群 = 排错序或内容截断。**

光靠文件名排序查不出「某段被截断了」，这个能。

### 4. 表格与混合语种的系统性处理

`references/text-conversion.md` 是一张规则表，**每一条都来自真实踩坑**：

- `+1.79%` → 上漲百分之一點七九
- 预测 PE 表格 → 三句叙述句，保留表头的限定语
- `alt／label` → 替代文字或標籤（纯缩写对听觉零信息量）
- `Liquid Glass` 保留（设计语言，人人都懂）
- `Ask About Screen` → 問螢幕（界面功能名，听众要的是功能不是设置菜单里的字符串）
- `——` 改句号（否则模型一路连读不换气）

判断准则不是「名词还是度量」，而是 **「听者能否解码这几个字母」**：`NVDA` 念出来还认得出，`PE` 念出来什么都不是。

### 5. 区分「事实」与「噪音」

**保留**：免责声明（`不构成投资建议`）—— 真实披露
**剔除**：调用日志（`先读取数据插件的使用说明`）、结尾抛给助手的问题、43 条参考文献
**但要说明剔了什么** —— 静默截断原文是歪曲，即使判断是对的

### 6. 不静默丢信息

公司代号、股票代码是**信息**。把「DA 與 RBV 差距」改写成「兩家公司」是错的。

要么念得出来（「D A 與 R B V」），要么在随附的口播稿里保留原样，让映射关系不丢失。
**静默删除一个名称，是这个项目明令禁止的失败模式。**

## 缺点（都实测过，不是猜的）

### 1. 判断环节无法自动化

`scripts/narrate.mjs` 只能做确定性的活。**「哪段是正文、哪段是元信息」「摘要要砍到多细」是判断，不是规则。**

所以这个 skill 加速的是工程部分，**内容部分仍然要人（或模型）逐篇过一遍**。这是它最大的成本，也是它最容易出错的环节。

### 2. 没有并行对照评测

规范要求的 producer vs baseline 评测**没跑成** —— 子代理环境不回报告。替代方案是真实调用验证：产出真交付物，并因此抓到了「STT 长音频返回 0 字」这个合成评测永远测不出的 bug。

**结论是这个 skill 经过真实使用检验，但没有量化的 A/B 对比。** 别把它当成「已验证优于无 skill 基线」。

### 3. 依赖 ffmpeg / ffprobe

合成、合并、校验都靠它。没装就得退化成一堆碎片文件 —— **那等于没解决问题**（用户要按一次播放，不是在手机上翻 57 个文件）。

### 4. 版本号读法会漂移

`17.0`、`16.x`、`Android 9`、`17.1` 这类要人工判断念法。规则表给的是示例，**不是完整覆盖**。新写法还得补。

### 5. 长文依然很长

一篇 7000 字的报告出来就是 35 分钟。**管线解决不了「内容本身太长」。** 真正要解决它需要删内容的判断，那是另一件事。

### 6. 图表、代码、公式没有处理规则

表格能线性化，**折线图、柱状图、代码块、数学公式目前没有规则**。遇到这类内容需要人先手改。

### 7. 中文数字 ↔ 阿拉伯数字的校验脆弱

STT 会把中文数字规范化回阿拉伯数字。所以 `--verify` 的键**必须写数字**；写「三百九十三点五」永远匹配不上。

反过来，某个数字偶尔因切片落点漏掉时，得先复跑确认是不是波动 —— 这个判断成本不低。

### 8. 依赖特定 TTS 供应商

脚本里的 `connector__matrix__batch_text_to_audio` 是写死的。工程编排本身与模型无关（换后端只需换那一个函数），**但「332 个音色、多语种、情绪控制」是供应商的能力，不是这个项目的**。

> 换句话说：**原料是供应商的，菜谱不是。** 别把菜谱的功劳算给原料 —— 那样会高估护城河。

### 9. 没有单元测试

质量证据来自一次真实干跑 + 一次真实生产调用。**够用，但不成体系。** 上游 API 若改了 `output_file` 字段名，那层防御会静默失效（脚本里有全量比对断言兜底，但没有测试锁住这个断言）。

### 10. 长文无并发控制

一篇 57 段的文章会连续发 6 次批量请求。没有并发、失败重试、也没有成本估算。

## 用法

```bash
# 1. 把改写后的分段写进 JSON（这一步是判断活，不是脚本活）
cat > segs.json <<'EOF'
{"segments": [
  "第一段，口语化之后的样子。",
  "第二段……"
]}
EOF

# 2. 合成 + 合并 + 校验
node scripts/narrate.mjs \
  --segments segs.json \
  --out output/my_article.mp3 \
  --verify "568.47,5.31,4125" \
  --keep-script output/my_article.md
```

输出：

| 标志 | 说明 |
|---|---|
| `--voice` | 音色 id，默认 `Chinese (Mandarin)_Reliable_Executive` |
| `--speed` | 0.5–2.0，默认 `0.95` |
| `--emotion` | happy / sad / angry / fearful / disgusted / surprised / neutral |
| `--gap` | 段间静音秒数，默认 0.5 |
| `--verify` | 承重数字，逗号分隔，**写阿拉伯数字** |
| `--no-stt` | 跳过回听校验（不推荐） |
| `--verify-only <f>` | 不重新合成，只对已有音档复验 |
| `--keep-script <f>` | 同时输出可阅读的口播稿 |

> `--verify` 的键**必须用阿拉伯数字**。STT 会把中文数字规范化回数字，写「三百九十三点五」永远匹配不上。

## 音色建议

默认：**沉稳男声 / 0.95 倍速 / 中性**（长文分析不催眠）。

完整对照见 **`references/voices.md`**（含语速档位、情绪、已验证/未验证清单）。

| 场景 | voice_id | speed |
|---|---|---|
| 默认 / 长文分析 | `Chinese (Mandarin)_Reliable_Executive` | 0.95 |
| 通勤赶时间 | 任意 | 1.15–1.2 |
| 睡前 / 放松 | `Chinese (Mandarin)_Warm_Bestie` / `Soft_Girl` | 0.85–0.9 |
| 正式播报 | `Chinese (Mandarin)_News_Anchor` / `Male_Announcer` | 1.0 |
| 电台 / 对谈感 | `Chinese (Mandarin)_Radio_Host` / `Lyrical_Voice` | 1.0 |
| 粤语 | `Cantonese_ProfessionalHost (M)` / `(F)` | 0.95 |
| 英文 | `English_CaptivatingStoryteller` | 1.0 |

完整目录 332 个（普通话/粤语/英/日/韩/西/法/德…）：
`mcode-tools connector call connector__matrix__get_voice_list --args '{}'`

> ⚠️ 表里的推荐是按场景推的，**不是 A/B 试听出来的**。粤语、英语、日语路径未实测。

### 合成之前先跑预检（不花任何 API 预算）

```bash
node scripts/preflight-all.mjs \
  --pair chip-research/ep12a_segs.json:chip-research/ep12a_keys.json:output/ep12a.md
```

一次抓出五类「会在合成阶段炸掉」的问题：

- **假键**：校验键不在稿子里 → 永远命中不了，会被报成「未命中」，白跑一轮 TTS+STT
- **损坏字符**：U+FFFD → `narrate.mjs` 载入时直接中止
- **超长段**：> 120 字 → STT 分片边界与 TTS 呼吸都受影响
- **段尾裸数字**：段尾是「8,」这种形状时，TTS 把它单独念出来最容易错（实测「20 億美元」→「21 億」）
- **md ↔ segs 不一致**：稿子改了但 segs 没重生成 → 音档与交付的稿子对不上

> 自动生成的校验键**也可能是假键**：`MI355X` 的 `355`、`gfx950` 的 `950`、`H100` 的 `100`、
> `Llama3-70B` 的 `70`、`P95` 的 `95`、`Qwen3-235B-A22B` 的 `235`/`22`、
> `GPT-5.5` 的 `5.5`、`Claude 4.7` 的 `4.7`、arXiv 编号 `2603.08713` —— 这些是型号与编号，
> 不是数据。把候选键当 regex 回代稿子，看**每个**出现位置：若全部落在型号内部，就是假键，删掉。

## 实战记录

| 文章 | 类型 | 段数 | 时长 |
|---|---|---|---|
| 腾讯「疑虑」机制分析 | 市场分析 | 10 | 5.2 min |
| 北方华创 002371 | 个股研究报告 | 10 | 5.6 min |
